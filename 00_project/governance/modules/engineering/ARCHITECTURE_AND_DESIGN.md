> Authority：ADR、设计质询、问题优先级和详细设计规则；由 `INDEX.yaml` 按触发条件加载。

# 8. 架构决策必须使用 ADR 记录

对于会影响未来开发的重要技术选择，应创建 ADR。

例如：

```text
ADR-001-use-qt6.md
ADR-002-use-tcp.md
ADR-003-reconnect-strategy.md
ADR-004-local-storage.md
```

每份 ADR 至少写清：

```text
# ADR-xxx：标题

## 状态
Proposed / Accepted / Superseded / Rejected

## 背景
为什么需要做这个决定？

## 约束
有哪些已知限制？

## 候选方案
方案 A
方案 B
方案 C

## 最终决策
选择哪个方案？

## 决策理由
为什么选择它？

## 代价与缺点
这个方案有什么明显代价？

## 影响范围
影响哪些模块、接口、测试或部署？

## 重新评估条件
什么情况下未来允许重新考虑这个决定？
```

AI 不得在没有说明原因的情况下推翻已经 Accepted 的 ADR。

如果确实需要改变：

1. 创建新的 ADR；
2. 说明为什么旧决策不再适用；
3. 分析影响；
4. 更新相关需求、设计和测试；
5. 旧 ADR 标记为 Superseded。

# 9. 设计阶段必须进行 AI 独立质询

在以下阶段完成后，应进行独立评审：

1. 产品需求完成后；
2. 系统需求完成后；
3. 架构设计完成后；
4. 详细设计完成后；
5. 大型代码修改完成后。

推荐使用另一个 AI、另一个上下文或一个没有参与原设计的审查角色。

审查 AI 的任务不是“帮助原设计辩护”。

审查 AI 的任务是：

> **主动寻找可能导致返工、故障、维护困难、测试困难或产品失败的问题。**

重点检查：

- 需求遗漏；
- 需求冲突；
- 隐含假设；
- 边界条件；
- 异常路径；
- 状态机；
- 并发；
- 多线程；
- 生命周期；
- 资源释放；
- 内存安全；
- 网络异常；
- 数据一致性；
- 接口定义；
- 协议兼容；
- 升级兼容；
- 错误恢复；
- 日志和诊断；
- 性能瓶颈；
- 长期运行；
- 安全风险；
- 可维护性；
- 可测试性；
- 部署风险；
- 硬件实际约束；
- 真实使用环境。

# 10. AI 连续质询规则

独立质询时必须遵守以下规则：

1. 每次只问一个最重要的问题。
2. 用户回答后，再问下一个。
3. 已经能从现有文档明确得到答案的问题不要重复问。
4. 能可靠推导的问题不要浪费时间质询。
5. 优先问会影响当前：
   - 产品设计；
   - 技术路线；
   - 架构；
   - 接口；
   - 数据结构；
   - 状态机；
   - 代码结构；
   - 测试设计；
   - 当前开发工作的事项。
6. 当前阶段还不需要处理的问题，记录为“后续质询项”，不要提前无限展开。
7. 建议按 `QUESTION_PRIORITY` 分类：

```text
QUESTION_PRIORITY P0：不回答就无法继续正确设计
QUESTION_PRIORITY P1：不回答可能造成重大返工或架构错误
QUESTION_PRIORITY P2：会明显影响当前代码质量、测试或维护性
QUESTION_PRIORITY P3：以后优化即可，当前可以暂缓
```

当前质询主要处理 `QUESTION_PRIORITY` P0、P1、P2。

结束条件：

> 当前阶段不存在尚未闭环、并且会显著影响产品设计、技术路线、接口、数据结构、软件架构、测试方案或当前代码实现的重大问题。

# 12. 详细设计必须先于正式编码

正式编码前，至少应明确：

- 模块边界；
- 模块职责；
- 公共接口；
- 输入；
- 输出；
- 数据结构；
- 状态机；
- 错误处理；
- 超时策略；
- 重试策略；
- 生命周期；
- 线程模型；
- 资源所有权；
- 配置；
- 日志；
- 数据持久化；
- 关键算法；
- 性能限制；
- 测试方法。

AI 不应仅凭一个模糊需求直接构建大量代码。

## 12.1 正式基线代码必须具有可恢复的设计意图

本节是 `Design Intent` 与规范系统语义边界的权威 Owner。

```text
NO BASELINED CODE WITHOUT RECOVERABLE DESIGN INTENT
```

任何新增或改变产品行为、并准备进入正式产品 Baseline 的代码，都必须能够追溯到与风险相称的明确设计意图。设计意图可以由以下一种或多种受控产物表达：

- 已批准需求或 Acceptance Criteria；
- ADR、架构或详细设计；
- 接口、行为或数据合同；
- 状态机、算法规格或关键不变量；
- 范围明确、已批准的 Task Intent。

设计深度按风险分级。低风险局部修改可以由 Task Intent、Acceptance Criteria 和直接验证证据承载；公共接口、状态机、安全约束、恢复规则、关键不变量或重大架构行为必须具有对应的显式规范产物。框架不要求为每一行代码建立独立设计文档，但不得让正式功能失去“为什么存在、应实现什么语义、受什么约束”的可恢复依据。

```text
CODE MUST NOT BE THE SOLE IMPLICIT
NORMATIVE SOURCE OF SYSTEM SEMANTICS
```

必须区分：

```text
Normative Truth
→ 系统正式应该做什么
→ 由批准需求、ADR、架构、设计、接口/行为合同、状态机和关键不变量维护

Implementation / As-Is Evidence
→ 系统当前实际上做什么
→ 由代码、测试、运行结果和日志提供证据
```

普通实现代码可以证明当前行为，但不得仅凭“代码已经这样实现”把行为提升为正式系统语义。状态机、公共接口合同、错误语义、安全约束、恢复规则和关键不变量不得只隐含在普通实现路径中；它们必须存在可独立读取、评审、追溯和恢复的规范表达。

机器可读 Schema、声明式状态机或与代码同仓的行为规格可以成为规范产物，但必须被显式指定为对应事实 Owner，并且能够独立版本化、评审和追溯。文件位于源码目录不自动使它成为普通实现代码，也不自动授予其规范权威。

允许以下受控例外：

- Spike、实验和原型可以先形成代码，但在补齐设计意图并完成适用接受前不得进入正式产品 Baseline；
- 紧急修复可以先止损，但在正式接受或 Release 前必须恢复最小设计意图、影响范围和验证依据；
- 生成代码追溯到受控 Schema、Generator、模型或机器可读规格，不要求逐行重复设计；
- Brownfield 迁移可以把代码作为 `As-Is Evidence` 恢复当前行为，但不得把未审查的现状静默提升为批准语义。

发现代码与规范产物不一致时，必须登记差异并由对应事实 Owner 判断是实现缺陷、文档过期还是正式变更；不得默认以代码覆盖设计，也不得默认以旧文档否定已验证的现实行为。

正式 C04 只在冻结 Review Scope 内检查：行为变化是否具有适当深度的设计意图、关键系统语义是否被普通代码隐式垄断，以及差异是否已经受控处置。不得借此要求全量重建未变化代码的设计文档。

# 13. 测试设计与测试代码必须分开

必须区分：

```text
06_test_design/
```

和：

```text
08_tests/
```

前者回答：

> 应该测试什么？

后者回答：

> 测试具体如何自动执行？

例如：

测试设计：

```text
REL-001：
系统连续运行 7 天不得发生进程异常退出。
```

测试程序可能是：

```text
08_tests/system/test_long_running.py
```
