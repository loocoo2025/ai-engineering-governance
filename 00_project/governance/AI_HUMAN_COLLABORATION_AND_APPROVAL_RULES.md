# AI 与项目负责人协作及审批可理解性规则

> 本文件是面向 Human Project Owner（人类项目负责人）的路线说明、阶段说明、审批材料可理解性和决定后反馈方式的唯一权威来源。
>
> 本文件不重新定义授权生命周期、保留决策边界、正式 C04、Current Truth、Gate、Baseline 或项目实例状态。机器必填字段见 `GOVERNANCE_EXECUTION_CONTRACTS.yaml`，授权与 `HUMAN_DETERMINATION` 语义见 `ROLE_INTERACTION_EXECUTION_POLICY.md`。

## 1. 核心原则

AI 不得只向项目负责人抛出“是否批准”。在请求任何正式决定前，必须先用项目负责人可以直接理解的语言说明：

- 整体路线和当前所处阶段；
- 本次要批准的文档、产物或决定是什么，以及它控制什么下游工作；
- 主要内容、变化、不做范围和未决问题；
- 关键术语、缩写和阈值的实际含义；
- 主要风险、取舍及推荐理由；
- 批准、要求修改、暂缓或拒绝分别会发生什么；
- 本次授权明确包含什么、不包含什么。

不得假设项目负责人已经逐字读完全部正文，也不得以提供文件路径代替解释。摘要用于支持理解，不成为第二 Current Truth；正式事实仍由对应 Owner 文件维护。

## 2. 事实所有权边界

```text
当前阶段 / Gate / 授权 / 下一步
→ CURRENT_STATE.md

当前有效决定
→ DECISION_INDEX.md

当前任务
→ ACTIVE_TASKS.md

当前未决问题
→ OPEN_QUESTIONS.md

反馈项当前状态
→ 12_issues/feedback/FEEDBACK_REGISTER.md

单次人工裁决内容
→ 对应 HUMAN_DETERMINATION_PACKAGE / 正式决定记录
```

本文件只拥有稳定的人类可理解性与呈现规则，不维护上述实例事实。

## 3. 分阶段协作

### 3.1 多阶段工作开始前

中等以上项目、重大功能或治理升级开始前，先说明：

1. 目标和最终交付物；
2. 主要阶段及依赖关系；
3. 每阶段建立或修改的主要产物；
4. 哪些阶段可以合并或暂缓；
5. 哪些内容已授权，哪些需要项目负责人决定；
6. 当前推荐路线、主要替代路线和停止条件。

项目负责人认可整体路线，不自动表示批准所有后续 Gate 或副作用动作；实际授权以精确 Authorization 为准。

### 3.2 每阶段开始前

说明阶段目标、全局位置、输入、输出、预计变更范围、不受影响范围、完成判据和阶段结束后预计请求的决定。

### 3.3 阶段执行中

- 在已授权边界内连续处理普通执行细节；
- 需要改变保留决策或超出授权时，按 `HUMAN_DETERMINATION` 路由停止；
- 新疑问、体验问题、治理缺口、改进建议或疑似缺陷先进入反馈登记；
- 不把普通技术选择包装成人工审批问题。

### 3.4 请求决定前

必须形成一个唯一、可绑定的 `HUMAN_DETERMINATION_PACKAGE`。不得只列文件名、只给结论或只问“是否批准”。

### 3.5 决定后

- 复述决定及其精确范围；
- 分别更新决定、当前状态、任务、未决问题或反馈的正确 Owner 文件；
- 说明下一步和仍未授权的事项；
- 不因一次决定自动扩大其他 Action Class 的权限。

## 4. 人工裁决包的可理解性要求

除机器合同要求的字段外，面向项目负责人的呈现必须让其能够回答以下问题：

某项不适用时仍保留对应字段，并写明 `NOT_APPLICABLE` 及理由；不得通过删除字段让信息缺口不可见。

### 4.1 我现在决定什么

用一句非专业化语言说明本次决定，以及为什么该事项需要人类权威。

### 4.2 它在整体路线中的哪里

```text
已经完成什么
→ 当前正在决定什么
→ 决定后准备做什么
```

### 4.3 主要产物是什么

对每份主要产物说明中文名称、用途、使用者、控制的下游工作和当前需要它的原因。

### 4.4 实际内容与变化是什么

摘要至少覆盖主要范围、不做范围、关键要求或取舍、与上一版本相比的变化、未决问题，并提供正式原文引用。

### 4.5 阈值意味着什么

每个待批准阈值必须说明数值和单位、适用环境、测量边界、包含与排除项、用户或项目影响、推荐依据、验证方法和未来变更方式。条件未冻结时明确标记 `TBD / UNKNOWN`，不得把候选值描述成已可验收事实。

### 4.6 风险与授权边界是什么

区分阻断问题、非阻断跟踪项、已接受取舍和尚未授权的后续工作，并明确列出：

```text
本次决定包含：
-

本次决定不包含：
-
```

### 4.7 有哪些选择

提供 `APPROVED / CHANGES_REQUESTED / DEFERRED / REJECTED` 及各自直接后果。正式 C04 仍只使用其自身的 `PASS / CHANGES_REQUESTED`，不得混用。

## 5. 术语与缩写

在每次面向项目负责人的独立输出中，缩写或专业术语第一次出现时，应给出英文全称和中文解释。受控 ID、代码、命令、配置键和 Schema 字段保持原样，在其外部补充说明，不改写机器内容。

## 6. 输出前检查

请求项目负责人决定前必须确认：

- [ ] 已说明结论和当前全局位置；
- [ ] 已说明主要产物是什么、有什么用；
- [ ] 已给出足以支持决定的内容与变化摘要；
- [ ] 未假设负责人已经读完正文；
- [ ] 首次出现的缩写和术语已解释；
- [ ] 阈值已说明环境、边界、实际含义和验证方式；
- [ ] 风险、取舍、不做范围和未决问题明确；
- [ ] 已明确本次决定包含和不包含什么；
- [ ] 已提供四种决定选择及后果；
- [ ] Package、Action、Scope 和 Target 唯一可绑定；
- [ ] 本次输出不会意外扩大授权。

任一必需项不满足时，不得直接请求“批准”。

## 7. 违反本规则时

如果项目负责人指出说明难懂、信息不足、缩写未解释、审批边界不清或默认其已阅读全文：

1. 先用清楚的中文重新解释；
2. 将意见登记到 `12_issues/feedback/FEEDBACK_REGISTER.md`；
3. 修正当前说明；
4. 需要改变正式产物或规则时，再按反馈分流建立对应 BUG、FIELD 或 CR；
5. 不要求项目负责人重复已经表达清楚的信息。
