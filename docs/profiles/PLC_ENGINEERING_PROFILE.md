本文件只拥有 PLC 专用工程约束。型号、I/O 表、参数、状态定义和验收值仍由项目原有需求、设计、接口文档维护，此处只引用，不能复制成第二份事实。

“必须/不得”指采用后适用的约束；“优先/默认”允许有实际依据的替代。普通取舍记在现有设计中即可。与批准需求、接口、架构或通用治理冲突时，指出具体冲突并停止受影响动作，请负责人裁决；不自动覆盖旧决定，不停止无关工作。人的纠正可以调整普通偏好，但不得被解释为自动豁免适用安全要求。

## 1. 目标：动作清楚，扫描可预测，现场能维护

在满足批准功能、时序和安全要求的前提下，优先选择最容易理解、定位故障和修改的实现，而非最短源码或最多抽象。

- 现场人员应能从主要维护入口查清：输出为何动作、为何不动作、由谁禁止、如何满足恢复条件。
- 每个重要状态和输出仲裁有明确负责位置；跨模块可以读取，不得无说明地互相覆盖。
- 新增抽象、状态副本、握手或生成步骤，需要说明实际用途、代价和更简单方案；普通局部函数不要求逐个新建 ADR。
- 不为假设中的跨品牌、跨机型或分布式部署建设通用引擎。已批准的变化点可以抽象。
- 不为精简删除联锁、换向保护、必要的受控停机或真实采样历史；也不把每层重复校验都包装成安全要求。

## 2. 当前设计所需的最小输入

从现有文档取得与本任务有关的事实；仅缺少会影响当前设计的项目才提问，不要求一次填完全部设备档案：

- CPU、固件、扩展模块、IDE/编译器、使用语言和指令限制；不默认所有 PLC 都按同一种扫描方式执行。
- 任务/中断、I/O 刷新与总线更新方式、周期和关键响应期限；容量、保持区和可用定时器/计数器。
- I/O 极性、断线含义、执行器反馈、动作顺序、停机方式和失效时的目标状态。
- 操作员、HMI、通讯和自动流程各自能发哪些命令，参数何时允许改变。

安全状态不等于所有输出一律清零。涉及人员或重大设备风险时，安全功能分配必须有批准的系统设计；普通程序和本 Profile 不替代安全回路、安全 PLC、厂商限制或所需合规证据。

## 3. 扫描与顺序控制

1. 明确本任务使用哪一次输入采样、何时计算、何时更新输出。按目标平台实际行为设计，不把普通循环扫描、立即 I/O、高速计数和中断混为一谈。
2. 优先使用清楚的顺控状态机和设备控制块。每个状态写明进入条件、动作、退出条件和故障/停止去向；小逻辑不强制套状态机。
3. 区分当前扫描值、上一扫描值、物理反馈和计算请求。上一扫描快照有实际时序意义时必须保留，不能按“重复变量”直接删除。
4. 多任务或中断共享数据时明确写入者及一致性方式；普通单任务内部无需凭空增加队列、消息总线或事务握手。
5. 循环和每扫描工作量应有界，不在扫描内等待设备完成。计时使用已确认的时基；不能把可变扫描次数直接当作固定时间。
6. 窄脉冲或快速变化超出扫描采样能力时，使用目标支持且设计批准的计数、捕获或中断机制，不靠扩大普通软件循环补救。
7. 顺序依赖须在相关设计或代码旁说明；不得仅凭“看起来等价”搬动保护、计量、状态更新和输出语句。

## 4. 命令、保护与物理输出

- 区分命令、期望输出、已下发输出和物理反馈；软件已写 OFF 不自动等于设备已停止。
- 同一物理输出的正常控制、手动操作和保护路径必须有明确优先关系及最终仲裁位置；独立硬件保护不受此软件单写入约束取消。
- 故障停止、正常停止、急停/安全功能和强制输出分别按批准设计处理，不能混成一个未经解释的布尔变量。
- 手动模式不默认绕过联锁。旁路、点动、强制输出及危险在线操作须有对应授权与现场条件。
- 上电、STOP→RUN、下载/在线修改和通讯重连：说明运行态、保持参数、累计量、待执行命令分别如何处理。不得仅因残留命令恢复危险动作。
- 自动恢复或恢复后的定时任务是否允许启动，由需求和风险决定；不默认“永远人工恢复”，也不默认“自动续跑”。
- 故障检测与恢复各有明确职责。配置接收处校验、运行异常监测、最终输出保护可以分别必要，不能机械合并；相同故障不要在多层各自无限重试。

## 5. 参数、通讯和数据

1. I/O 和 HMI 地址使用一份权威映射，明确类型、宽度、单位、范围、读写权限及保持属性。映射改变需核对真实消费者，不把“内部重命名”当成地址兼容。
2. 外部值在可信接收边界校验。数组下标、除数、量程和输出映射不能仅靠“上位机会保证”的注释；要有对应实现/配置依据，或在 PLC 边界拒绝无效输入。
3. 明确参数立即生效、空闲生效或下次启动生效。运行中需要稳定的数据采用快照、锁定写入或平台支持的一致提交方式；不得先删除快照再假设外部不会写。
4. 多寄存器参数、配方更新和重复命令要明确完整性与生效边界；只有真实一致性需求才增加握手，不套用分布式事务。
5. 计量与控制运算明确单位、缩放、取整、溢出、计数回绕及采样有效性。按实际精度和资源选择整数/定点/浮点，不一律禁用浮点。
6. 区分配方、标定、累计量与临时运行态。保持或清除策略按实际保持区和掉电行为确认；累计量不因普通首扫初始化被误清。
7. 通讯超时、传感器无效或数据陈旧按批准行为处理；避免把无效测量悄悄当成零或一直沿用旧值。

## 6. 可读性、资源和生成代码

- 业务变量用有含义的名字，状态码提供就近可查定义。数组适用于同类通道，不应仅为少写初始化语句就隐藏全部业务语义。
- 指定主要维护入口：手写源码，或语义源文件＋生成器。生成产物不与源文件双向手工维护；现场改动须回到权威源后受控再生成。
- 采用生成器时保留精确输入、工具版本、输出和源到输出映射。避免仅靠易受文本排版影响的多轮替换承担未经验证的行为变换；已有生成链不因此自动重写。
- 容量、扫描时间和可读性分别评价。减少行数不等于减少指令步数，减少步数也不等于满足响应期限；优化收益用目标工具或实际测量说明。
- 不规定通用的层数、行数或容量百分比。资源余量由目标、运行负载和已批准扩展需求决定；不为不可见收益牺牲现场维护性。
- 先消除已确认的重复表达、无效转换和多余复制，再考虑改变结构；清理必须保持求值、时序和副作用语义。
- 诊断应能追踪当前状态、禁止原因、命令来源及相关反馈，不要求为每个中间位建立日志、事件库或新框架。

## 7. 设计、增量评审与验证

C02 在现有设计中交代本次输出/状态归属、扫描依赖、关键停止与恢复行为，以及新增复杂度的理由；简单变更可用简短说明，不另造文档套件。

C04 只审本次 Target 的适用接受条件及直接回归，重点问：输出因果是否可追踪？状态与写入是否冲突？时序/联锁是否被改变？新增层和转换是否必要？不因采用本 Profile 自动新增正式 C04。触发、独立性及判定仍以通用框架的保障政策与正式评审规则为准。

C05 按通用测试政策选择最小充分证据，以下是触发式选择，不是每次全跑清单：

| 改动涉及 | 选择对应证据 |
|---|---|
| 顺控或输出 | 受影响正常路径、停止/故障路径及关键联锁 |
| 保持区、启动或命令消费 | 相关重启/重连场景，确认旧命令和配置分别处理 |
| 时基、负载、快速输入 | 目标周期/响应证据及相关漏采风险 |
| 参数、地址或配方 | 边界拒绝、生效一致性及消费者兼容 |
| 生成/容量优化 | 精确生成产物、相关行为回归及真实容量收益 |

编译、仿真、离线回放、台架和现场证据分别标注；编译成功不能证明物理动作安全，模拟重启不能替代必要的实体掉电验证。已有有效证据复用，不默认重跑全部。无法完成必要的硬件验证时记录缺口，不宣称通过，也不擅自连接、下载或动作设备。

非核心改进先登记，不因风格偏好无限返工；涉及当前接受条件、权限或安全的真实问题仍按既有规则处理。负责人决定是否采纳普通改进，AI 不自行扩大工作。
