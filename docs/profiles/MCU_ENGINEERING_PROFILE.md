> 状态：可选模板，复制或阅读不等于项目正式采用。
> 文档标识：MCU_ENGINEERING_PROFILE；修订日期：2026-09-27。

## 1. 目标：按时完成，故障可控，代码能维护

- 在批准功能、时限和安全要求下选择最简单可维护的结构。代码少不是唯一目标，层多也不等于可靠。
- 区分硬件访问、设备行为和工艺逻辑的职责，但不强制每项都建一层、一个接口、一个任务或一个仓库。
- 优先使用现有成熟驱动和清楚的局部函数；不为单一设备提前建设跨芯片插件、通用事件总线或动态服务框架。
- 新增任务、队列、锁、状态副本、包装层或生成器，要能对应实际时序、并发、复用或变更需求。小改动在现有设计中说明即可，不逐个创建 ADR。
- 已批准变化点可以抽象；没有依据的未来扩展先不做。不要为了本 Profile 重写稳定模块。

## 2. 当前设计所需的最小输入

按任务从现有文档取得：MCU/板卡版本、时钟、工具链、启动与链接配置、RAM/Flash、外设与引脚、电源/复位行为；关键周期、响应期限、输入/输出含义和通讯契约。

执行方式由实际需求选择：

- **裸机主循环/协作调度**：适用于能以有限步骤和明确周期完成的任务；不因“专业”默认加 RTOS。
- **RTOS**：有实际并发、隔离或时限调度需求时采用；不机械规定“一模块一线程”。
- **中断/DMA/硬件定时**：用于已识别的低延迟或吞吐需求；不把所有业务逻辑塞进中断。

不预设芯片品牌、语言、操作系统、协议或固定内存余量。缺少决定当前安全/时序行为的事实才暂停提问，其他后续细节允许按需补齐。

## 3. 执行、并发与时间

1. 每项关键工作明确运行上下文、触发条件、允许执行时间、超时后果及数据/资源负责位置；记录在现有设计，不建全量运行台账。
2. 中断服务程序（ISR）只做有界且时限需要的工作。不要在 ISR 中等待互斥锁、阻塞通讯、写持久存储或执行无界日志/分配；延后处理要有确定的交接方式。
3. RTOS 中使用目标内核和端口允许的中断 API，并核对中断优先级限制；`FromISR` 名称本身不代表任何优先级都能调用。
4. 共享变量明确谁写、谁读、何时一致。`volatile` 不是互斥、原子性或跨 DMA 缓存一致性的保证；根据实际 MCU、编译器和内核选择原子操作、短临界区或同步机制。
5. 队列、环形缓冲区、DMA 缓冲区明确容量、生命周期、满/空行为与归属转移；涉及缓存时按目标要求处理一致性。不向异步消费者传递已失效的局部数据地址。
6. 等待和重试有适合当前操作的上限或取消机制。关键控制路径不能被慢速日志、通讯或持久化长期阻塞；空闲等待可使用合适的阻塞机制，不以忙轮询冒充实时性。
7. 锁范围保持短小，避免持锁执行慢 I/O；多个锁确有必要时说明顺序。优先检查能否通过单一资源管理位置减少共享，而不是继续叠锁。
8. 区分单调运行时钟、墙上时间和采样时间。处理适用的计数回绕、时间单位和周期抖动；校时不能意外破坏控制超时。
9. DMA 完成、驱动调用成功、报文发出和设备执行成功是不同事件。异步边界需要真实完成/失败语义，同步函数内部不凭空增加多轮确认协议。

## 4. 内存、数值与持久数据

- 对 RAM、栈、Flash 和关键缓冲区建立与实际负载相称的预算；栈高水位等测量只是覆盖场景证据，不是绝对最坏情况证明。
- 优先使用边界清楚的静态或有界存储。动态分配不是一律禁止，但需说明使用阶段、上限、失败行为和碎片风险；硬实时路径不引入无界分配行为。
- 数组、报文长度、指针生命周期、整数转换、单位和溢出在可信边界处理；不要在每个内部函数重复同一检查，也不能因为“调用者应保证”省掉不可信输入检查。
- 整数、定点或浮点由精度、量程和目标性能决定；避免无收益的来回转换，不预设有硬件浮点单元。
- 参数校验在接收/装载边界进行，明确原子生效或快照策略。通讯回调不得直接覆盖正在使用的半份配置。
- 非易失存储（NVM）区分配置、标定、累计量与临时状态。存在写入时明确掉电一致性、损坏识别、恢复值和写入寿命；不因扫描/循环频繁写 Flash。
- CRC 等完整性校验不能冒充来源认证；是否需要认证由真实攻击面和批准要求决定。
- 数据结构、配置版本或存储布局变化需处理已有数据的兼容，不能用静默清空配置代替迁移。

## 5. 物理控制与故障恢复

1. 控制命令、期望状态、已下发状态与物理反馈分别表达。每个执行器有明确仲裁位置，手动、自动和保护命令不得无规则地竞争写输出。
2. GPIO 上电电平、复用切换、外设初始化、欠压/复位期间的输出由软硬件共同设计；应用初始化函数尚未执行时，不能假设软件已保证安全。
3. 安全状态按危险分析与批准需求确定，不等于所有输出一律 OFF。普通 MCU 软件不能替代所需硬件保护、安全系统或合规证据。
4. 说明复位、看门狗、掉电与通讯恢复后如何处理残留命令和任务。不默认自动恢复危险动作；需要自动恢复时明确适用条件。
5. 故障检测、上报、抑制输出、清除与恢复有明确职责。复位错误标志不等于故障已经消失，不无限重启掩盖持续故障。
6. 采用看门狗时，喂狗依据能反映关键工作健康；不能由一个仍活着的独立定时器无条件掩盖主控制卡死。也不为每个普通函数创建心跳。
7. 传感器无效/过期、执行器不响应和通讯丢失按批准行为降级或停止；相关超时由实际设备和风险确定，不拍脑袋写统一数值。

## 6. 通讯、诊断与维护

- 协议明确单位、字节序、长度、有效范围、超时、重复命令和错误含义；只针对实际协议，不默认加入会话身份、事务和多层重试框架。
- 重试由明确位置负责，总次数/时间和副作用可控。重复执行会导致危险动作时，按真实风险设计去重或命令确认。
- 日志保留定位当前故障所需信息并控制缓冲与输出负载；日志失败不能拖垮关键控制。不要默认记录每次中断、每个采样点或所有中间状态。
- 芯片、HAL/驱动、RTOS、编译器或优化参数变化需评估实际受影响行为；不自动扩大成全部平台兼容测试。
- Bootloader、OTA、双分区与远程运维均为可选功能，不因模板自动开发。采用升级功能时明确镜像/目标校验、写入中断恢复、配置兼容及可行的救援路径；真实性与回退限制按批准安全要求处理。
- 烧录、擦除、改保护位、在线强制输出、远程升级和运行电机阀泵属于不同副作用，不因获准改代码就自动获准执行。

## 7. 设计、增量评审与验证

C02 在现有设计中记录本次设计意图、运行上下文、资源归属、关键时间/故障语义及新增复杂度的理由；不把治理角色照搬为运行时任务。

C04 只审本次 Target 的适用接受条件与直接回归：共享状态是否一致？生命周期/边界是否有效？关键时限是否被慢操作影响？故障输出是否正确？新增抽象是否必要？本文件不新增正式 C04 触发点，触发、独立性和结论仍由通用框架管理。

C05 按通用测试政策选择最小充分证据；以下按改动触发，不是每轮全跑：

| 改动涉及 | 选择对应证据 |
|---|---|
| 纯算法或状态转移 | 主机侧正常、关键边界及相关历史缺陷回归 |
| 外设、中断、DMA、时钟 | 目标构建及必要的板上时序/数据一致性验证 |
| 任务、锁、队列或内存 | 相关竞争、超时、溢出和资源余量证据 |
| 输出或恢复路径 | 受影响启动、停止、故障、重启行为；必要硬件确认 |
| Flash、配置或升级 | 对应损坏/中断恢复、兼容和实际写入约束 |

主机测试、交叉编译、仿真、台架和现场证据分开标注；不能用主机通过证明 ISR 时序或真实引脚安全。必要硬件条件缺失时记录缺口，不虚报完成、不自动接入设备。EMC、压力、长稳、模糊或全协议组合测试仅在真实需求/风险触发时执行，已有有效证据尽量复用。

非核心问题先登记，不为所有可能性增加防御代码。是否处理普通改进由负责人决定；已批准的安全与接受条件仍须满足。严禁用“代码更简单”掩盖已知的关键内存、时序或安全错误。
